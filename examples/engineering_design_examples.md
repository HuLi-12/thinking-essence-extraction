## 示例 1：为什么唯一索引要包含 deleted 列

### 问题背景

MySQL 表中，为了支持软删除，通常在唯一索引中包含 `deleted` 列。
如果不包含，软删除一条记录后无法再插入相同唯一键的记录。

**【常见说法】**
防止重复数据，实现软删除。

**【问题】**
"防止重复"是功能描述，不是机制解释。为什么软删除必须在唯一索引中包含 deleted 列？
逻辑删除的本质矛盾是什么？

**【真正变化的变量】**
直接变量：
- 唯一索引的 key 组合：(uk_columns) → (uk_columns + deleted)
- 每行记录存在"是否被删除"的状态标志

衍生变量：
- 逻辑删除的单行：deleted=1，对唯一约束视为"不存在"（但实际存在）
- 唯一约束的作用域被 deleted 列扩展：同一条业务记录可存在"deleted=0 的活跃版本"和"deleted=1 的已删除版本"
- 并发插入场景下，deleted 列的值需要保证唯一性（通常用时间戳或递增 ID 填充）

**本质一句话**
唯一索引包含 deleted 列的本质不是"防止重复"，而是**在唯一约束中引入一个额外的状态维度**，
使"业务上唯一"和"逻辑上可重复"的矛盾得以调和——同一条业务键值可以有一个活跃版本和多个已删除版本共存。

**【机制链】**
业务唯一约束 by (user_id, type)
→ 软删除将某条记录的 deleted 设为 1
→ 此时 (user_id, type, deleted=1) 的唯一约束保持存在
→ 再插入 (user_id, type, deleted=0) → 如果唯一索引是 (user_id, type)，则冲突
→ 如果唯一索引是 (user_id, type, deleted)，则新记录 (..., deleted=0) 与已删除记录 (..., deleted=1) 不冲突
→ 但如果 concurrent 插入两条 (..., deleted=0) → 仍会冲突（需要应用层保证或分布式锁）

**【代价交换】**
以索引存储空间增加（deleted 列占用额外字节）和写入时 deleted 值冲突管理为代价，
换取软删除功能与唯一约束的共存，风险是并发场景下 deleted 列不能保证全局唯一。

**【可验证】**
1. 并发插入两条 (uk_fields, deleted=0) → 数据库报唯一约束冲突。
2. 先用 deleted=1 写入一条记录，再插入 (uk_fields, deleted=0) → 成功。
3. 如果 deleted 只填固定值 0/1，第二条 deleted=0 仍然无法插入 → 所以 deleted 通常填入时间戳或主键 UUID。

## 示例 2：为什么 ThreadLocal 用完必须 remove

### 问题背景

Java Web 应用中，用户信息通常存入 ThreadLocal，请求结束后如果不 remove，
线程池复用时可能读到脏数据。

**【常见说法】**
ThreadLocal 用完不 remove 会内存泄漏。

**【问题】**
"内存泄漏"是结果描述，不是机制解释。到底是谁引用了谁？为什么在线程池里更危险？

**【真正变化的变量】**
直接变量：
- 当前线程的 ThreadLocalMap 新增 entry，key 是 ThreadLocal 弱引用，value 是业务对象强引用
- entry 数量随请求次数递增（线程池场景）

衍生变量：
- key（弱引用）可能被 GC，但 value（强引用）仍被 ThreadLocalMap 持有 → value 泄漏
- 下一个请求复用同一线程 → ThreadLocalMap 残留上次 entry → 可能读到脏数据
- 线程池线程长期存活 → 泄漏的 entry 永远不会被清理

**本质一句话**
ThreadLocal remove 的本质不是"释放内存"，而是**主动切断线程池中长生命周期线程对短生命周期请求数据的引用链**，避免线程复用时发生两种问题：value 对象无法被 GC（内存泄漏）和前请求残留数据污染后请求上下文（数据污染）。

**【机制链】**
请求进入 → 用户信息写入 ThreadLocal
→ 线程池线程不会随请求结束销毁
→ 业务对象（value）被该线程的 ThreadLocalMap 强引用
→ 如果不 remove → value 无法 GC → 内存泄漏
→ 下一个请求复用该线程 → ThreadLocal.get() 读到旧 value → 上下文污染

**【代价交换】**
以每次请求结束时显式清理（try-finally remove）的编码成本，换取线程复用场景下的内存安全和上下文隔离。

**【可验证】**
1. 固定线程池大小为 1，第一个请求写入 userId=1，不 remove。
2. 第二个请求不写入 userId，直接 get() → 如果读到 userId=1，说明发生上下文污染。
3. 长期运行场景：监控 ThreadLocalMap size 是否持续增长。

## 示例 3：为什么 Redis 缓存要加随机 TTL

### 问题背景

高并发系统中，大量缓存 key 同时过期会导致缓存雪崩——请求全部穿透到数据库。

**【常见说法】**
防止缓存雪崩。

**【问题】**
"雪崩"是现象描述，不是机制解释。为什么同时过期会导致雪崩？随机 TTL 改变了什么变量？

**【真正变化的变量】**
直接变量：
- TTL 从固定值（如 3600s）改为固定值 + 随机偏移（如 3600 + rand(0, 600)）
- key 的过期时间分布从集中变为均匀

衍生变量：
- 任意时刻点，过期的 key 数量从"全部"降为"一部分"
- 缓存穿透的瞬时并发量从 N（总 key 数）降为 N/窗口宽度
- 数据库连接池的瞬时负载峰值显著下降

**本质一句话**
Redis 随机 TTL 的本质不是"防止雪崩"这个结果，而是**将 key 的过期事件从完全同步的周期脉冲变为均匀分布的时间序列**，从而把集中于一点的缓存穿透压力分散到更长的时间窗口内。

**【机制链】**
固定 TTL：所有 key 在同一时刻写入 → 同一时刻过期
→ 所有请求同时 miss 缓存 → 全部穿透到 DB
→ DB 连接池瞬间被打满 → 请求排队、超时、雪崩

随机 TTL：各 key 过期时间错开
→ 任意时刻只有少量 key 过期
→ miss 请求分散 → DB 负载在安全范围内
→ 雪崩概率大幅降低

**【代价交换】**
以缓存有效时间的微小不确定性（最长与最短相差随机窗口大小）为代价，
换取过期事件的均匀分布，消除周期性的并发穿透峰值。

**【可验证】**
1. 模拟 10000 个 key，固定 TTL：统计每秒过期 key 数量（应该是 0 → 10000 → 0 的脉冲）。
2. 随机 TTL：统计每秒过期 key 数量（应该是平稳分布）。
3. 对比两种策略下 DB 的 QPS 峰值。

## 示例 4：为什么延迟双删不能保证强一致性

### 问题背景

缓存更新场景中，延迟双删（先删缓存 → 更新 DB → 延迟再删缓存）被用来解决缓存与数据库的一致性问题。

**【常见说法】**
延迟双删保证最终一致性。

**【问题】**
"最终一致性"是结果标签，不是机制解释。延迟双删到底解决了什么并发问题？它不能解决什么并发问题？

**【真正变化的变量】**
直接变量：
- 操作顺序：del cache → update DB → sleep → del cache
- 两次删除之间的时间窗口

衍生变量：
- 第一次删除后到第二次删除前的窗口期内，可能已有并发请求回写了旧数据到缓存
- 第二次删除清除了这个旧数据，但窗口的存在意味着短时间内的不一致
- 如果 sleep 时间小于并发写入的间隔，第二次删除可能发生在正确的写入之前

**本质一句话**
延迟双删的本质不是"保证一致性"，而是**用一个短时间窗口的不一致（第一次删后到第二次删前）来换取缓存与数据库最终达成一致的概率**。它无法消除窗口期内的不一致，也无法在窗口期内保证强一致性。

**【机制链】**
请求 A：del cache → update DB = 1 → sleep...
请求 B（并发）：读 cache miss → 从 DB 读到旧值 0 → write cache = 0
→ 此时缓存是旧值 0
A 醒来：del cache again → 清除旧值 0
→ 下次读从 DB 取到新值 1 → 一致

但若 sleep 不够：
请求 B 的 write cache 发生在第二次 del 之后
→ 缓存又变成旧值 0
→ 不一致

**【代价交换】**
以 sleep 带来的写入延迟增加和窗口期内不一致的风险为代价，
换取高概率（非绝对）的最终一致性。

**【可验证】**
1. 模拟高并发读写，验证延迟双删后缓存与 DB 的一致率。
2. 对比不同 sleep 时间下的不一致概率。
3. 对比使用分布式锁的方案：延迟双删 vs 锁 + 双删的一致性和延迟差距。
